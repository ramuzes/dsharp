# Agent roster — reusable role templates for team members

## Change 2026-11-27 — model tiers, resident members, yield after dispatch

Evidence: one implementation session (2026-11-26). The lead created six developer members for six task dispatches (plus one code reviewer), passed an explicit model on five of the eight spawns (the template's base model on none of those five) and never returned to it, and held one turn for 5 h 20 min with 28 `wait_agent` calls (11 at the 10-minute cap).

- ADDED: **model tiers.** A template carries a *base model* (the existing `defaultModel`, unchanged in storage) and an optional *high-tier model*. The agent-facing `roster_spawn` no longer accepts a model; the lead chooses a **tier** and the plugin resolves it from the template.
- MODIFIED: `roster_spawn` parameters are `{ template, task?, tier?: 'base' | 'high', reason? }`. `tier: 'high'` requires a non-empty `reason` and a template that has a high-tier model; otherwise it is refused. The result reports the member name, whether an existing member was reused, and the model applied.
- ADDED: the **escalation basis** is stated to the model in the tool description and is the same on every call: (1) every new task starts on the base model; (2) a rework may move to the high tier only after one rework on the base model failed to pass; (3) a task brief that itself names the high tier may start there — escalation is a decision of the plan, not of the lead at dispatch time. The tier follows the task, never the role: a high-tier task does not make the next task high-tier.
- ADDED: every high-tier dispatch is **recorded** (time, session, template, member, reason) and listed on the Settings page, so escalation can be audited against its basis.
- ADDED: **resident reuse.** A template carries a reuse policy, `role` (default: one standing member per role *and model route*) or `task` (a new member per task). Under `role`, `roster_spawn` gives the task to an idle member of that template and model route if one exists and creates one otherwise — including when the only member is busy, so parallel work is never queued behind a resident member. The rule is identical for base, high-tier and dialog-chosen models; a high-tier member of a role is therefore a separate member the lead manages alongside the base one.
- ADDED: the tool description tells the lead to **end its turn** once nothing is left but waiting: the runtime queues a member's completion notice as the lead's next turn when the lead is idle (`packages/subagent/subagent/src/manager.ts:1151`), so polling with `wait_agent` is unnecessary.
- Decision record: ADR-0013.

## Change 2026-11-25 (b) — command-driven creation and standby members

- REMOVED: the injected member instruction. The composer path is the user speaking by definition, so it rendered as a user bubble and cost a lead turn.
- ADDED: the dialog stages its request (`agentRoster.stageSpawn`, one-shot per session, expiring) and runs a bare `/roster` — the `/compact` path: two log-only lifecycle events in the transcript, no model message, no lead turn.
- ADDED: standby semantics. A member's opening frames the role as identity and, without a task, orders it to stand by; delivery is `caller` without a task (no settle notice, the lead is never woken) and `parent` with one.
- KEPT: `roster_spawn` for the lead's own use in conversation, under the same opening and delivery rules. Decision record: ADR-0012.

## Change 2026-11-25 — per-spawn model override

- ADDED: the "+" dialog carries a **member model** picker (model and reasoning effort) that starts from the template's default and may override it for this one spawn — including "inherit the session model", which clears a template default. The template itself is never edited by it.
- MODIFIED: `roster_spawn` gains an optional nullable `model` argument. (REMOVED again for the agent by the 2026-11-27 change below, which replaced it with a tier; the dialog's override is unaffected.) (The dialog stated the choice in the injected instruction at the time; change (b) above stages it with the request instead, so from the dialog it never passes through a model.) Precedence: an explicit object or `null` beats the template default, which beats inheriting the session route; an omitted argument keeps the pre-change behavior.

## Change 2026-11-23 — agent-driven member creation (form 2)

- REMOVED: AI-assisted drafting in every form — the draft session, the `draft` remote, the Settings toggle/draft-model block, the four draft Config fields, ADR-0010's mechanism. A template IS the instruction the user would otherwise type; nothing must write it for them.

## Requirement (the why & what)

### Problem statement

DSH's agent teamwork requires users to specify subagents explicitly, in conversation, every time. Switching to a new session means re-describing the same role's responsibility boundary and main goal to the lead agent from scratch, and re-stating which model that member should run on. Users who repeatedly collaborate with the same roles (reviewer, tester, docs writer…) have no way to configure that description once and reuse it across sessions.

### Goal

A new plugin, **agent-roster** (package `dsh-agent-roster`), that turns a profile-wide **roster of role templates** into one-click member creation:

- a **role template is exactly what the user would otherwise say to the lead agent**: a name, a one-line description, the standing instruction (responsibility boundary and main goal), and an optional model preference;
- from the composer's "+" menu, picking a template (plus an optional one-off task) **creates the member through the `/roster` command** — recorded in the transcript like `/compact`, with no message from the user and no turn of the lead — and the member **stands by** until it is given work;
- the template's model preference is applied **reliably** at creation (it cannot be left to prompt interpretation — see the design note);
- from the session, the member's model and reasoning effort can be **overridden for that one spawn** — including back to "inherit the session model" — without editing the template;
- templates are managed once in Settings and are reusable in every session;
- from a session, the lead **stays on the template's base model by default** and escalates to a high-tier model only on a stated basis, so cost is predictable and every escalation is explainable;
- a role's member is **reused across tasks** when the template says so, instead of a new member per task;
- after giving a member its task the lead can end its turn; the member's completion starts the next one;
- the plugin UI is fully bilingual (Chinese and English); all docs and code comments are English.

### User stories

1. As a session user, I want to pick a role template from the "+" menu and get a member that stands by, so that I never re-describe the role's boundary, goal, and model again — and without a long message appearing in my conversation or a turn of the lead spent on it.
2. As a session user, I want to attach a one-off task to the pick ("review the payments module"), so that the same role can be pointed at this session's work.
3. As a session user, I want the transcript to record the creation as a compact command entry, like `/compact`, so that I can see later when a member joined.
4. As a session user, I want a freshly added member to wait for work instead of inventing some, so that adding a member never costs me an unsolicited report or a turn of the lead.
5. As a roster owner, I want each template to carry a model preference that is actually used, so that cheap work runs on a cheap model without prompt-stuffing.
6. As a session user, I want to give one member a different model or reasoning effort than its template default, just for this spawn, so that the template stays a sane default and this one member gets what the task needs.
7. As a roster owner, I want to create, edit, and delete templates on the plugin's Settings page, so that the roster stays curated without touching YAML.
8. As a session user, I want to ask the lead agent in conversation to save the role we just used as a template, so that templates capture real working context.
9. As a Chinese- or English-language user, I want every plugin surface in my language.
10. As a roster owner, I want to give a role a base model and, optionally, a high-tier model, so that routine work runs on the cheap model and the choice of the strong one follows a rule I set rather than the lead's judgement at dispatch time.
11. As a roster owner, I want the lead to have to state why a task went to the high tier and to see those records in Settings, so that I can correct the plan or the template when escalations are unjustified.
12. As a session user, I want a role's member to take the next task of that role instead of a new member being created each time, so that the team works as a team and the Subagents panel stays readable.
13. As a session user, I want the lead to stop and wait for members by ending its turn, so that it does not poll every ten minutes and I can talk to it while members work.

### Out of scope

- AI-assisted template drafting of any kind (removed — the user writes the instruction, or distills it in conversation).
- An in-dialog ad-hoc role: a one-off that is not worth a template goes through ordinary conversation instead.
- Model-facing `agent_preset` selection (surfacing templates as presets to the `subagent` tool) — still deferred.
- Member lifecycle UI (rename, interrupt, delete): the host's Subagents panel and agent tools cover it.
- Team task-board UI (owned by the host's agent-team package); template import/export; cross-profile sync.
- An agent-supplied model on `roster_spawn` (removed in this change — the lead picks a tier; a concrete model is the user's choice in the dialog or on the template).
- Knowing which member came from which template across a host restart: the plugin's member registry lives in memory, so after a restart the first request for a role creates a fresh member.
- The host's own wording that tells a lead to "wait for required teammates" (`packages/team/tool-agent-team/src/index.ts:31`); this change counters it in the tool description only.
- Verifying the escalation basis mechanically: the plugin records the lead's reason, it cannot audit a review outcome.

## Design (the how)

### Solution

The plugin has a small host half and a client half. The host half owns the roster (a storage-domain table), exposes template CRUD, the high-tier dispatch records and `stageSpawn` as a Remote for the Settings page and the dialog, registers the `/roster` command and the `roster_spawn` agent tool over one spawn — which resolves the lead's tier to a model route and hands a task to an idle resident member before creating one — and keeps the authoring tools `roster_template_save/list`. The client half adds one "+"-menu command whose modal lists templates, takes an optional per-spawn model and first task, and on confirm stages the request and runs `/roster` on the session. Members appear in the standard Subagents panel.

The user flow: click "+" → "Add agent member" → pick a template → optionally pick the member model and reasoning effort (it starts from the template's default) → optionally type the task → confirm. The transcript gains a compact command entry naming the member; the member starts under the current tree's root with the template's standing prompt as its role and **stands by** — or starts on the first task when one was given.

### Implementation decisions

**Why a plugin tool instead of letting the agent call `subagent` directly.** Two facts force it: (1) DSH limits explicit child-model selection on the `subagent` tool to the parent's current route unless the Host sets an allowlist policy (`packages/subagent/tool-subagent/src/model-selection.ts:167-190`, `MODEL_ROUTE_NOT_ALLOWED`), so "this member runs on model X" cannot be reliably honored through the model's own tool call; (2) the template's standing prompt must stay frozen — letting the lead rewrite it on every spawn reintroduces the drift templates exist to prevent. `roster_spawn` therefore does the deterministic host-side spawn (`subagents.startActivation` with `agentOptions`), while the agent loop still contributes what it is good at when the lead itself creates a member from the conversation. The dialog does not need that contribution: the user supplies the task, so it creates the member through `/roster` without a model call at all (ADR-0012).

**Creation through a command (client).** Confirming stages the request — template, per-spawn model, first task — through `agentRoster.stageSpawn` (a one-shot request bound to the session that expires; the template is resolved at staging, so an unknown one fails in the dialog), then admits one command line on the session: `ctx.sessions.using(sessionId, { source: 'agent-roster' }, ref => ref.binding.session.command('/roster'))`. The line is bare on purpose: a request lost in between (host remount, expiry) then answers the usage text instead of silently creating a member with the template defaults and none of the user's choices (`packages/api/session-controller/src/client/sessions/session.ts` `command()`: "the full command line, leading slash included… the host executor durably logs the lifecycle; outcomes render as flow nodes, never as a response echo"). A command is the host's act-without-a-model-message path: `execute()` appends `command/run` before the handler and `command/done` at settlement, both log-only (`packages/interaction/commands`; `/compact` is the first-party reference). The dialog therefore sees only the admission `{ matched }`; `matched: false` means the host has no `/roster` and is reported. A refused staging or admission renders a bilingual error and runs nothing.

**`/roster` (host command) and the member opening.** `/roster` is a global command. With a staged request of the invoking session it uses that request (a typed argument beside it must name the same template; otherwise the command refuses and the request stays pending); typed as `/roster <template name or id>` it adds that template's member with the template's default model and no task; with neither it answers its usage. It resolves the template, calls the same `spawnFromTemplate` as `roster_spawn`, and reports `Member "<name>" (<template>) created and standing by. Model: …` or `… created and given its first task. …`; every failure becomes model-safe text. The member's opening message — its first user message, never its system prompt — frames the template's standing prompt as identity ("who you are for your whole residency — not a task to perform now"). Without a task it orders the member to stand by: nothing inherited from the creating session (timeline trees, plans, titles, repository state) is an assignment; do not explore or produce work; do not send a message; reply with one short line and end the turn. With a task it states the first task. Delivery follows the same split: `parent` with a task (the member owes the lead its result), `caller` without one (`notifySettlement` returns before the settle notice, so a standby member never wakes the lead, and it still enters the parent catalog). The 2026-11-25 incident — a bare role prompt read as a task, the inherited tree title taken as its topic, the settle notice waking the lead — is what these rules exist to prevent.

**`roster_spawn` (host tool).** Parameters `{ template: string, task?: string, tier?: 'base' | 'high', reason?: string }` — `template` accepts the record id or its exact name; `tier` defaults to `base`; `reason` is the lead's one-line basis and is required with `high`. It resolves the template and the tier to a model route (below), then either hands the task to an idle resident member of that template and route (below) or creates one. Creation calls `subagents.startActivation` with `label` = template name, `name` = slugified template name (then `-2`, `-3`… among the root's existing children; `lead` yields `lead-member`), `prompt` = the member opening described above, and `agentOptions` from the resolved route (a template without a base model lets the child inherit the parent's route). The result is `{ name, reused, model, tier }` as model-safe text. Typed errors: `roster/bad-request` (missing or empty `reason` with `high`), `roster/no-high-tier-model` (`high` on a template that has none — the text says to add one in Settings or use the base tier), `roster/not-found`, `roster/ambiguous-name`, `roster/no-subagents` (defense in depth — the tool only registers when the runtime is injected, see below).

**Model tiers.** The template's base model is its existing `defaultModel`; the high-tier model is a new optional field of the same shape. `base` resolves to the base model, `high` to the high-tier model; neither can name a model the template does not carry, so the lead can no longer select an arbitrary model or inherit its own. The escalation basis lives in the tool description verbatim, in three rules: every new task starts on the base model; a rework moves to the high tier only after one rework on the base model failed to pass; a task brief that names the high tier may start there. The description also says the tier follows the task, not the role. The 2026-11-26 evidence for the last sentence: after one escalation the lead kept five later spawns on the high-tier model, including a routine one. The plugin does not judge the basis; it records every `high` dispatch — time, session, template, member, reason — in a plugin-owned storage-domain record and lists the newest entries on the Settings page under the template manager.

**Resident reuse.** A template's reuse policy is `role` (default) or `task`. Under `role`, before creating, the tool looks for a member of the caller's tree that the plugin itself created from the same template with the same resolved model route and that is currently idle (`activity: 'inactive'` in `subagents.listDescendants`); a member registry the plugin keeps in memory maps a member's session id to its template and route. An idle match receives the task as an agent message through the subagent runtime's own member messaging (`subagents.sendMessage` from the tree's root, with the tool's abort signal); its opening is not repeated — the member keeps the standing instruction it was created with — and the message states that this is a new task from the lead. With no task, an idle match is simply reported (a standby request for a role that already stands by wakes nobody). With no idle match — none exists, or every one is busy — a member is created exactly as before, so a busy resident never queues work behind itself. The result says whether the member was reused, so the lead can tell a familiar member from a new one. Dialog-created members enter the registry with the model the user chose, which makes them reusable under the same rule.

**Per-spawn model override.** The dialog's picker starts from the template's default (a default the session catalog does not list stays selectable through a lossless synthetic row, so a degraded catalog never blocks the choice); switching templates resets it to the new template's default (a pick is remembered per template while the dialog stays open, so switching back restores it); changing only the effort keeps the model in effect; choosing another model starts that model on its own default effort, and re-picking the template's model restores its stored effort. From the dialog the choice is staged with the request and never passes through a model; the member it creates is not subject to the tier rules, because the user — not the lead — chose the model. Through `roster_spawn` the lead chooses a tier only (above); the tool's result reports the model actually applied.

**Yield after dispatch.** The tool description tells the lead that once nothing is left but waiting it should end its turn rather than call `wait_agent`: the runtime delivers a member's completion to an idle lead as its next turn and to a working lead at its next step. The host's team guidance still says the lead "must wait for required teammates before giving the final answer"; the plugin does not contradict the obligation, only the polling — not giving a final answer and not holding a turn are different things.

**Registration and availability.** The tools callback injects `['tools', 'subagents']` — `roster_spawn` resolves the caller's tree root and the subagent runtime through that second service, and cordis throws when a callback touches a service it did not inject. The mount therefore records `tools-pending` after `done` and lets the callback overwrite it with `tools-registered` / `tools-failed`; a host that never provides those services (a deployment without the subagent runtime) stops at `tools-pending` rather than claiming a terminal success. In that deployment the plugin can do nothing useful anyway: member creation is its core capability. `/roster` registers on its own callback (`commands`, `subagents`) so a host without the commands service keeps `roster_spawn`; whichever callback lands last writes one terminal record naming both mounts (`tools-registered { authoring, command }`, or `command-registered` when only the command has mounted; failures write `tools-failed` / `command-failed`).

**Roster storage** stays a plugin-owned storage-domain table of zod records `{ id, name, description, prompt, defaultModel?, highTierModel?, reuse?, createdAt, updatedAt }` — the two new fields are optional with defaults (`reuse` reads as `role` when absent), so records written before this change load unchanged. The high-tier dispatch log is a second table of the same kind. An in-memory fallback plus a loud status record covers the absent service. Config holds only `exposeAgentTools` (the authoring tools); `/roster` serves the dialog and `roster_spawn` the lead; both are registered regardless of the toggle.

**Remote surface**: template CRUD (`listTemplates`, `saveTemplate`, `deleteTemplate`) plus `listHighTierUse` for the Settings record list. No spawn, no team-status probe, no draft.

**Settings section** (`settings.section`, id `agent-roster`): the roster manager — list, add, edit, delete, per-template base model, optional high-tier model, reuse policy — and below it the high-tier dispatch records (newest first, bounded). No AI-draft block.

**Shared UI**: the model chooser is the host model-picker dropdown pattern (CSS anchor positioning + portaled `MenuSurface` + provider-grouped rows, copied and renamed per the practices rule); the same `ModelRefEditor` (model plus reasoning effort) serves the Settings template editor and the dialog's per-spawn override. Templates are chosen in the same host-style dropdown (name-only rows, the selected template's description under the trigger), so a large roster scrolls inside the menu instead of overflowing the dialog.

### Testing decisions

- **Unit (node --test)** — strict fakes as before (inject-only proxy scopes, wrapper-typed config, zod-validating storage fake, a subagent-runtime fake with the real activation signature, a session fake with the real `command()` contract). New coverage: the member opening and delivery rule; the `/roster` handler (staged versus typed, the pending-request refusal, usage, cancellation, disposal order); `roster_spawn` resolves by id and by exact name, rejects unknown/ambiguous templates, applies the per-spawn model precedence (explicit object or `null` > template default > inherit; an invalid explicit model — wrong shape, empty provider or model, or an empty effort — rejects with `roster/bad-request`), writes the member opening (identity framing, a stand-by order or the first task), applies the delivery rule (`caller` without a task, `parent` with one), and allocates names; `/roster` consumes the staged request of its session or a typed template, answers its usage otherwise, and reports every failure as text; `stageSpawn` validates, resolves the template immediately, and stages one request per session. `saveTemplate` refuses a default model with an empty provider or model through a write-time schema stricter than the read schema, so one stored record written before the rule still loads and cannot take the listing down; the high-tier model gets the same rule, and a template with no default model may not carry a high-tier model. Tier resolution: `base` → the template's base model, `high` → its high-tier model; `high` without a reason, with a blank reason, or on a template without a high-tier model is refused with the typed errors above; a template with no base model lets `base` inherit the session route. Reuse: with an idle registered member of the same template and route the task is delivered through the runtime's member messaging and no activation starts; with a busy member, a member of another route, an unregistered member, or reuse policy `task`, a member is created; a request without a task reports an idle match without messaging it; the registry records every member the plugin creates or the dialog stages.
- **Client tests** render against real React (`react-test-renderer`): command contribution, template list, task field, the staged request and the bare `/roster` command line (never a `prompt()` call), failure lines (refused staging, unmatched or refused admission), and the per-spawn model picker (prefill from the template default, override, inherit, effort coupling, reset on template switch, an effort-only change keeping the template model, an override remembered per template). A wrong-typed `tier` or `reason` argument is rejected by the real `@deepseek-ai/dsh-tools` execute wrapper with `INVALID_ARGS` before the plugin runs (`tests/tools.spec.js` pins it, as it did for `model`). The Settings editor is covered for the high-tier model field (optional, validated like the base model) and the reuse selector, and the record list for its empty and populated states. The removed surface (the agent-side `model` argument) must leave no dead reference in the tool schema. The removed surfaces (draft, team gating, name field) must leave no dead references.
- **Live-host verification**: background host, stage records, served boot graph, then: template CRUD round-trip; "+" → template → confirm leaves `command/run` + `command/done` for `/roster` in the session log and **no** `user/message` from the dialog, with the command node naming the member; a member added without a task settles **without** a settle notice reaching the lead; a member given a first task reports its result back; a typed `/roster <template>` adds a standby member with that template's defaults; the per-spawn model override reaches the child session's `modelSelection`; a `roster_spawn` with `tier: 'high'` and a reason runs the member on the template's high-tier model and writes a dispatch record; a second `roster_spawn` for the same template and tier, after the first member has settled, reuses it (no new session directory, a new turn in the member's log) while the first member is still running it creates a sibling; after the reuse the lead's log shows the member's settle notice starting a new lead turn.

## Further notes

- Decisions: ADR-0008 (spawn through the subagent runtime — the mechanism is unchanged; the caller is now the tool), ADR-0009 (storage-domain persistence), ADR-0011 (member creation through a plugin tool), ADR-0012 (the dialog creates members through `/roster`; members stand by), ADR-0013 (model tiers with a stated escalation basis; resident members), ADR-0010 (draft session — superseded).
- Version: the change ships as agent-roster 0.3.0 (new capability: tiers, reuse, dispatch records), not a patch.
- The `subagent` runtime appends its own result-delivery guidance to the child's first message; the plugin does not duplicate it.
- The plugin declares its engine constraint per repo packaging conventions and carries no runtime npm dependencies.
