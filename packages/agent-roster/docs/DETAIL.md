A role template is exactly what you would otherwise type to the lead agent: a name, a one-line description, the standing instruction (responsibility boundary and main goal), an optional base model, an optional high-tier model, and a reuse policy.

From the composer's "+" menu you pick a template, optionally override the model and add a first task, and confirm. The plugin runs the `/roster` command, which the transcript records the way it records `/compact` — a compact command entry with its outcome, no message from you and no turn of the lead. The member is created with the template's standing prompt (frozen, never rewritten) as its role and **stands by**: it is told explicitly that nothing inherited from your session is an assignment and that work will arrive through messages or the shared task board. A first task typed in the dialog becomes its first assignment, and its result is then reported back to the lead. `/roster <template name or id>` can also be typed directly. The lead agent can give work to members itself with the `roster_spawn` tool, under the same rules.

**Model tiers.** The lead does not pick a model: it names a tier, `base` or `high`, and the member runs on the template's model for that tier. Every new task starts on `base` (the session model when the template has no base model). `high` needs a written reason and a template with a high-tier model, and is refused otherwise. The rule the lead is given: move to the high tier only after one rework on the base model failed to pass, or when the task brief itself names it — the tier follows the task, never the role. Every high-tier dispatch is recorded with its reason, and the newest 50 records are shown in Settings under the templates so you can check each one against the plan. A template accepts a high-tier model only together with a base model. Should a record fail to be written, the lead's tool result carries a warning instead.

**Resident members.** A template says whether its member is reused **by role** (the default) or **by task**. By role, an idle member of that role and model takes the next task and a new one is created only when none is idle — parallel tasks still get their own members. A member on the high-tier model is a separate member from the base one. The rule is the same whether the request comes from the lead's `roster_spawn`, the "+" dialog with a task, or a typed `/roster` command: a role that already has an idle member on the same model is not given another one, and the command entry says the member is already in the team. A request without a task adds no member either: it returns the idle member's name, the command entry says the member is already in the team and standing by, and nobody is woken. By task, every task gets a new member, for work that should stay isolated. Only members of your own team are considered, and which member belongs to which role is remembered only until the plugin is reloaded or the host restarts; after that the first request for a role creates a member.

**Waiting.** After giving members their tasks the lead ends its turn; a member's completion notice starts the lead's next turn.

Manage templates in **Settings > Agent roster**: create, edit, delete, set each template's base model and optional high-tier model (through the same model picker the rest of the harness uses), and choose the reuse policy. The `roster_template_save` / `roster_template_list` tools let the lead agent distill the role you have just been using into a template from inside the conversation; the `exposeAgentTools` option hides those two authoring tools when a deployment wants the model to stay out of the roster.

The member's model and reasoning effort can be overridden for a single spawn from the same dialog. The picker starts from the template's base model; choosing "inherit the session model" clears it for this member. The template itself is never edited; from the dialog your choice is handed to the host directly and never passes through a model. Such a member runs on the model you chose, not on a tier.

Members are ordinary subagents: they appear in the host's Subagents panel and in `list_agents`, and nothing about them is rendered by this plugin.
