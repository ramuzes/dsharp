角色模板就是你本来要对 leader 说的那句话：名称、一句话描述、常驻指令（职责边界与主要目标）、可选的基础模型与高阶模型，以及成员复用方式。

“+”菜单里选一个模板，可选地覆盖模型、填写首个任务，然后确认。插件运行 `/roster` 命令，会话记录对它的呈现方式与 `/compact` 相同——一条紧凑的命令记录及其结果，对话里不会出现你“说”的话，也不占用 lead 的一轮。成员以模板的常驻指令（冻结、不被改写）作为角色被创建，并**待命**：它会被明确告知，从你的会话继承来的任何内容都不是给它的指派，工作会通过消息或共享任务板送达。在弹窗里填写的首个任务会成为它的第一项指派，完成后结果回报给 lead。`/roster <模板名或 id>` 也可以直接输入。lead agent 自己也能用 `roster_spawn` 工具给成员派活，规则相同。

**模型档位。** lead 不挑选模型，只指定档位 `base` 或 `high`，成员运行在模板为该档位配置的模型上。每个新任务都从 `base` 开始（模板未配置基础模型时即会话模型）。使用 `high` 必须写明理由，且模板配置了高阶模型，否则会被拒绝。lead 遵循的规则是：只有在基础模型上的一次返工仍未通过、或任务说明本身指明高阶时才升到高阶——档位跟随任务，而不是角色。每次高阶派发都会连同理由记录下来，设置页的模板管理器下方显示最近的 50 条，便于对照计划核查。模板只有在配置了基础模型时才能配置高阶模型。若记录写入失败，lead 收到的工具结果会带一条警告。

**常驻成员。** 模板决定其成员是**按角色复用**（默认）还是**按任务复用**。按角色复用时，该角色在相同模型上的空闲成员接手下一个任务，只有没有空闲成员时才新建——并行任务仍各有成员。运行在高阶模型上的成员与基础成员是两个不同的成员。无论请求来自 lead 的 `roster_spawn`、带任务的“+”弹窗，还是直接输入的 `/roster` 命令，规则都相同：同一角色已有相同模型上的空闲成员时不会再添加成员，命令记录会显示该成员已在团队中。不带任务的请求同样不会添加成员：它返回空闲成员的名字，命令记录显示该成员已在团队中待命，且不会唤醒任何人。按任务复用时每个任务都新建成员，适合需要相互隔离的工作。只在当前团队树范围内查找可复用成员；成员与角色的对应关系只在插件本次加载期间保留，插件重载或宿主重启后，第一个请求会新建一个成员。

**等待。** 派发完任务后 lead 即结束本轮；成员的完成通知会开启 lead 的下一轮。

在 **设置 > Agent roster** 管理模板：新建、编辑、删除，为每个模板设置基础模型与可选的高阶模型（使用与 harness 其它地方一致的模型选取器），并选择成员复用方式。`roster_template_save` / `roster_template_list` 工具让 lead agent 在对话中把刚用过的角色沉淀成模板；`exposeAgentTools` 选项可隐藏这两个写作工具，供不希望模型接触花名册的部署使用。

成员的模型与推理力度可以在同一个弹窗里针对本次生成单独覆盖：选取器以模板的基础模型为起点，选“继承当前会话模型”则这位成员不再使用模板的基础模型。模板本身不会被修改；从弹窗做出的选择直接交给宿主，不经过任何模型。这样创建的成员运行在你选定的模型上，而不是某个档位。

成员就是普通的子代理：出现在宿主的 Subagents 面板与 `list_agents` 中，本插件不渲染任何成员列表。
